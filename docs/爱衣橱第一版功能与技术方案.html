爱衣橱第一版功能与技术方案

方案建议稿 · 2026年10月15日 · 面向网页端 · 开源能力已查公开资料，模型效果与成本尚待实测

用用户自己的衣服，推荐愿意穿的搭配，并展示接近个人体型的上身预览。

推荐采用开源 Web 框架和图片处理组件搭建产品，使用多模态模型识别衣物、辅助搭配，使用 GPT Image 验证身材底图与上衣加裤子的组合预览。衣橱、推荐约束、偏好、数据关联和生成任务管理由团队开发。第一版不训练基础模型，不依赖尚未完成授权核对的 VTON 默认管线上线。

一 产品边界与第一版目标

第一版只证明一件事：用户录入自己的上衣和裤子后，能够选出一套愿意穿的搭配，并获得保留这两件衣物主要特征的个人体型预览。

默认先覆盖日常休闲与通勤，固定正面成人模特；具体首发人群与风格作为上线前的产品决策，不假定男装、女装的效果可以互相替代。网页适配手机浏览器，方便拍照入库。

  • 衣物管理：上衣、裤子为核心；裙装、外套、鞋可登记、收藏并出现在单品搭配图中。
  • 推荐范围：第一版主链是上衣加裤子，鞋和外套可作为补充。衣橱缺少类别时如实提示。
  • 真人预览范围：先支持上衣加裤子的两件组合；裙装、外套叠穿、鞋包替换不计入本版承诺。用户在生成前就能看到该范围。
  • 身材表达：身材相近的视觉参考，不承诺厘米级复现、真实尺码判断或面料物理仿真。体重与围度不直接等同于二维轮廓。

不纳入首版：购买导购和电商抓取、社交社区、真人照片换脸、三维人体、视频、多角度、自动判断松紧、尺码推荐、模型训练与大型推荐系统。天气先允许手动选择冷热和雨晴，自动天气接入作为可延后项。

三 三条用户流程

第一次使用

登录 → 设置少量风格偏好 → 上传几件上衣与裤子 → 确认识别结果 → 选择标准模特或生成个人底图 → 获得搭配 → 查看单品组合 → 按需生成预览 → 收藏。底图生成不阻塞衣橱与推荐功能。

每天使用

选择场景与冷热 → 查看已有衣物组成的推荐 → 换一件或保留喜欢的组合 → 查看预览 → 标记今天穿了。若有最新可用天气信息，可代填条件并允许用户修改。

围绕一件衣服

打开裤子详情 → 点击“帮我搭配” → 锁定裤子 → 推荐候选上衣 → 用户替换与收藏 → 生成所选组合预览。所有入口共用同一推荐接口，不做两个独立推荐系统。

四 三条 AI 链路

A 衣物识别与整理

  1. 校验文件实际格式、大小和尺寸，标准化方向，移除无关 EXIF 信息；原图与派生图分开存储。
  2. 先检查是否为单件、主体是否完整。首发以平铺或清晰单件商品图为主要支持输入；真人穿着图仅在验证通过后开放，复杂背景不承诺自动抽取。
  3. 多模态模型返回受约束的结构化字段：类别、主色、图案、领型、袖长、裤型、可见风格、需用户确认项。
  4. 可选抠图只用于缩略图与拼图。抠图失败可以回退到裁剪原图；不补画被遮挡的图案，不覆盖原始衣物。
  5. 用户确认后成为可推荐衣物。用户修改优先于后续自动标签。

B 从个人衣橱生成推荐

  1. 从服务端身份确定用户，读取其已确认且可穿衣物，按场景、温度与明确禁忌筛选。
  2. 按上衣和裤子形成候选。第一版从结构化标签与业务规则开始，不强制引入向量数据库。
  3. 向模型提供有限候选的图片、标签和 ID，要求输出衣物 ID、槽位与一句理由；锁定单品与排除项作为硬条件。
  4. 服务端验证归属、存在性、类别、可穿状态、锁定项和去重。无效输出有限重试，之后用可解释规则兜底；无合理组合则提示补充衣物。
  5. 记录曝光、收藏、替换、实际穿着与负反馈。早期以用户明确偏好和最近行为调整排序，不宣称已经训练出个性化模型。

FashionCLIP 是可选的图文检索组件，不等于穿搭推荐器。相似的两件衣服不必然适合搭在一起。需要检索时再加 FashionCLIP 与 pgvector，中文查询可先使用经核对的英文标签映射，并单独评测。

C 身材底图与上身预览

  1. 准备授权明确、同姿势同背景、穿贴身基础服装的成人模特模板。用户数据先转换成比例与轮廓描述，再请求编辑；不把输入围度直接写成已实现的成图测量值。
  2. 生成少量候选，用户确认。保存模板、身体资料版本、底图图片、模型与提示词版本。
  3. 组合预览输入为已确认底图、上衣原图、裤子原图与对应槽位。鞋与外套即便出现在推荐里，也明确不属于该次真人预览范围。
  4. 优先测试一次多图编辑完成两件换装。顺序换装仅作为实验备选，第二步必须重新核查第一件；不能把单件测试成绩当成组合成绩。
  5. 每次新的搭配以已确认底图为人物来源。已生成的试穿图不成为新的身材底图。固定随机种子也不能当作身份锁定保证。
  6. 检查两件衣物主要特征、脸、发型、姿势、轮廓、遮挡和残留原衣；自动检查只作筛查，固定样本由人工复核。复杂文字印花先标记实验支持或限制输入。
  7. 失败允许有限重试，保留单品图和原图对照。结果展示 AI 预览标识，不由生成图给出实际尺码结论。

GPT Image 支持参考图片编辑，但人物一致性与遮罩精度存在限制，必须用实际输入建立验收数据集。OpenAI 官方说明

FASHN 官方模型卡报告输出 576×864、约 8GB 推理显存，也承认体型保持不完美与原衣残留。这些是作者报告，不是本产品的性能承诺。放大输出不能恢复原图已经丢失的服装细节。官方模型卡

六 推荐系统架构与部署

用户浏览器　Next.js 　↓ 登录态、上传授权、衣橱与搭配请求 业务 API　FastAPI 　├─ PostgreSQL：用户、衣物、底图、搭配、任务、额度、反馈 　├─ 私有对象存储：原图、抠图、缩略图、底图、预览图 　└─ RabbitMQ → Celery Worker 　　　　　　　　├─ 图片整理与可选 BiRefNet 　　　　　　　　├─ 多模态识别与搭配 API 　　　　　　　　└─ GPT Image Adapter 　　　　　　　　　　后续可接 VTON GPU Worker 浏览器轮询任务接口 ← 数据库中的明确任务状态

初期保持一个业务服务与独立 worker，不拆成大量微服务。生产使用 HTTPS、托管数据库、私有对象存储、消息队列与备份。API 路线不需要常驻生成模型 GPU；本地抠图仍需评测 CPU/GPU 开销，也可暂时保留裁剪图。

建立三类独立适配接口：classifyGarment、recommendOutfits、generatePreview，另有 generateBodyBase。供应商变更不改变衣橱和搭配业务结构。接口统一不代表不同模型支持相同衣物类别或组合能力，要保存能力声明并由前端限制入口。

API 密钥只在服务端。图片以短时签名链接或服务端传输交给供应商；所有上传与下载先验证资源归属。上线部署地区、模型服务可用地区、数据处理条款和天气服务授权需要在选定服务商后核对，不假定某地区一定可直接调用。

登录优先接入一个已有托管身份服务，团队负责用户与业务数据的关联。短信、邮箱、社交登录先选择一种正式支持方式，其他入口后续扩展；服务商和计费是待定配置，不在本稿编造。

七 核心数据与接口边界

  • UserProfile：用户、偏好、场景与可选城市；BodyProfile：身体参数及版本，和普通推荐偏好分开。
  • MediaAsset：owner、对象地址、类型、校验值、派生来源、删除状态、保留策略。
  • Garment：owner、原图、缩略图、类别、标签、人工修改、版本、可穿状态和确认状态。
  • ModelTemplate / BodyBaseVersion：素材授权记录、身体资料版本、图片、确认状态、模型与提示词版本。
  • Outfit / OutfitItem：推荐上下文、理由、各槽位衣物 ID 及版本；不以文字名称代替关联。
  • GenerationJob / Preview：底图版本、衣物版本、模型配置、输入快照哈希、请求 ID、状态、结果和检查结论。
  • Feedback / WearLog：推荐反馈、成图反馈、穿着时间，分开记录。
  • QuotaLedger / ModelRun：额度预占与释放、实际计费、供应商任务状态、幂等键与失败类别。

最小接口集合：上传授权与提交、衣物 CRUD、身体资料与底图生成确认、推荐搭配、替换槽位、创建与查询预览任务、收藏、反馈、穿着记录、删除个人数据。推荐和替换都必须重新检查衣物归属与当前状态。

任务状态建议为 queued → running → succeeded / failed / cancelled，并为上游超时增加 unknown 状态进行结果核对。上游超时不等于未计费；不能立即重复调用。worker 重复投递时依赖数据库幂等锁与供应商请求标识恢复。

去重键包含用户、底图版本、衣物 ID 与版本、模型、提示词和生成配置；用户主动“再生成”创建新尝试 ID。衣物或底图更新后旧结果可作为历史查看，但不显示为当前搭配预览。删除衣物、图片或账户后，阻止任务继续发布结果；按策略清理数据库、对象存储与派生文件，并处理备份保留期限。

八 实施顺序与研发分工

以下是实施关卡，合起来构成第一版，没有编造工期和人数。通过标准未达成时修正对应能力，不把技术演示直接作为公开发布。

  1. 先验证组合预览。使用授权测试素材比较 GPT Image 与许可允许的备选，分别验证单件、上衣加裤子、不同体型；评估延迟与可用结果成本。前端同时完成流程原型，服务端建立资源与任务模型。
  2. 完成衣橱和推荐。上传、识别确认、CRUD、真实 ID 推荐、锁定与替换、单品拼图、收藏与反馈形成可用闭环。生成未就绪也能完整体验选搭配。
  3. 接入身材与预览。底图确认和版本、两件组合、任务状态、限额、重试、原图对照与结果检查全部接入。
  4. 小范围真实使用。检查用户是否愿意录入和实际采用推荐，按失败类型修正。若组合预览未达标，明确保留为实验能力；此时不能宣称原定完整版已验收。

角色分工：产品与设计定义首发人群、标签、场景、异常文案和判断样本；前端负责入库、衣橱、搭配和任务体验；服务端负责权限、数据、规则、队列、额度与适配；AI 工程负责提示词、质量评测和可选 GPU 服务；测试与运维负责权限隔离、任务恢复、备份与成本告警。可由同一人兼任，不预设团队编制。

资源不足时的削减顺序：自动天气 → 图文向量检索 → 次要风格入口 → 衣物批量处理便利功能 → 更多模特模板。优先保留衣橱真实关联、推荐换件、两件组合验证、失败反馈和数据权限。不能通过省掉业务校验换取“看起来已经能推荐”。

九 验收指标与成本口径

下面的数量和阈值是建议测试口径，不是实测成绩，也不是行业标准；在首发人群与预算明确后可以调整。

功能与权限必须通过

  • 推荐衣物归属、存在性、类别与锁定约束通过率 100%；无有效候选时不生成虚构衣物。
  • 相同提交在并发点击与队列重放时只创建一次业务任务；上游超时进入核对流程。失败额度与实际服务商费用分账记录。
  • 跨用户资源访问、删除后结果发布、旧搭配绑定错图、刷新丢任务等关键案例全部通过。

图像质量单独验收

建立 5 种测试体型 × 10 套上衣裤子组合的 50 组固定输入，每组至少生成两次，共 100 次。覆盖深浅颜色、条纹、印花、宽松与修身；文字和复杂材质另外分组。另测同一模特编辑前后的脸、姿势与背景一致性，以及长袖换短袖等原衣残留案例。

每张图同时满足两件衣物主色、领口袖长、裤型、主要图案正确，且无明显人脸、肢体、姿态或体型漂移，才算可用。衣服穿上后轮廓会受版型影响，不以外轮廓像素相等判定体型相同。建议普通支持样本首次可用率达到 80% 再进入小范围验证；同时报告最多两次尝试的可用率、每类表现与尾部等待时间，不能只选最佳展示图。

推荐价值单独验收

建议邀请 10 位目标用户各录入至少 5 件上衣和 5 条裤子，在衣橱与天气允许时进行 3 次真实场景任务。观察录入完成率、修改标签负担、至少一套愿意穿的会话占比、换件率、收藏与实际穿着。可以暂以 70% 会话能选出一套愿意穿的搭配作为试运行目标；成图漂亮不能替代该指标。

成本先测量再决定收费

每张可用预览成本 = 全部生成尝试、失败重试、检查、图片处理及分摊基础设施费用 ÷ 可用预览张数。另记入库识别成本、一次推荐成本、底图生成成本、存储与流量。自部署还要计入 GPU 空闲、冷启动、运维和许可成本。

先显示单品拼图，用户点击后才生成真人预览；底图按版本复用；同一配置结果可按用户意图复用；限制并发、尝试次数和每日额度。单次时延、P95 等待时间、单日预算与付费方案待实测确定，不承诺几秒出图或固定单张价格。

十 上线前需要定下的事项

  • 首发具体人群、模特覆盖范围与最常见场景，用于确定测试衣物和风格标签。
  • 目标市场与部署地区、身份服务、识别推荐服务商、图像模型可用性与数据处理要求。
  • 每张可用预览可接受成本、等待时间、免费额度与超限处理。
  • 固定模特素材的授权范围；用户图片与身体数据的告知、删除、存储期限和第三方处理方式。
  • 有无 GPU 和模型服务维护能力。没有也可先完成 API 路线，不因此阻塞推荐与衣橱开发。

这些事项影响上线配置与验收范围，不影响先建立功能、数据和任务架构。最重要的技术未知是两件真实衣物在目标人群体型上的保真程度，最重要的产品未知是用户愿不愿意录入衣橱并采用推荐。
